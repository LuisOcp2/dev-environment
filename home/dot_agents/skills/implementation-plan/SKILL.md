# Implementation Plan

## Objective

Turn an ambiguous request into a concrete plan that a reviewer can approve,
a developer can execute in order, and a tester can verify, before any
production code is written.

## When to use

- A feature spanning more than about three files.
- Any change involving a data migration, a public API, or a deployment.
- Work that would take more than a session and must survive a context reset.
- When Luis asked for a plan, a design, or "how would you approach this".
- Before delegating work to another agent or session.

## When not to use

- A trivial, well-understood change: a typo, a constant, a one-line fix.
- A pure research question with no implementation.
- Mid-execution: when the code is already being written and the plan would
  be stale.

## Required inputs

- The request, in Luis's words.
- The repository, already explored with the `discovery` skill, or enough
  context to explore it now.
- Any hard constraints: deadline, compatibility, budget, stack preference.

## Procedure

1. **Restate the goal in one sentence.** If the request contains two unrelated
   goals, split them into two plans. Do not silently do both.

2. **List the acceptance criteria** before any technical detail. These are
   checkable statements. Ask Luis to confirm them if any is ambiguous.

3. **Inventory the files.**
   - Create: new modules, new tests, new config entries.
   - Modify: with a one-line note on what changes in each.
   - Read only: context needed but untouched.
   - Never edit by hand: generated files, migrations already applied, lockfiles
     regenerated by a tool.

4. **Extract the design decisions.** Where two reasonable choices exist, write
   a one-line recommendation and a one-line reason. These are exactly what a
   reviewer should spend attention on.

5. **Name the risks, in a table.** For each: what can go wrong, how likely,
   how bad, and the mitigation. Include backward compatibility, data
   migration, concurrency, performance, security and rollout.

6. **Define the tests before the phases.** Each acceptance criterion needs at
   least one test. Name the file each test will live in. For a bug fix, name
   the input that reproduces the bug.

7. **List validation commands that already exist** in the project. Detect
   them from `package.json`, `Makefile`, `pyproject.toml`. Never invent a
   script name.

8. **Split into phases**, each independently revertible:
   - Phase 1 must produce real signal: a failing test, a skeleton that
     compiles, a spike that answers a question.
   - No phase may depend on a later phase.
   - Each phase lists its own exit criterion.

9. **Define done** as checkable conditions, not intentions.

10. **Write the open questions.** Anything only Luis can answer. Stop and ask
    before implementing if a question blocks the design.

## Constraints

- Do not write production code in this skill.
- Do not include work that is not required by the acceptance criteria.
- Never plan a command or script that does not exist.
- Never plan to skip, delete or weaken an existing test.
- Prefer the smallest design that satisfies the criteria; note when a more
  complex design is justified.

## Validation checklist

- [ ] Goal restated in one sentence
- [ ] Acceptance criteria are checkable
- [ ] File inventory: create / modify / read-only / never-edit
- [ ] Design decisions carry a recommendation
- [ ] Risks table with mitigations
- [ ] Tests mapped to acceptance criteria, with file names
- [ ] Validation commands exist in the project
- [ ] Phases are ordered, independent and individually revertible
- [ ] Definition of done is checkable
- [ ] Open questions listed

## Mandatory output format

```markdown
## Goal
<one sentence>

## Acceptance criteria
- [ ] <checkable statement>
- [ ] <checkable statement>

## Scope
**Create**
- `path` — <contents>

**Modify**
- `path` — <what changes>

**Never edit by hand**
- `path` — <why>

## Design decisions
| # | Decision | Options | Recommendation | Why |
|---|----------|---------|----------------|-----|

## Risks
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|

## Tests
| Acceptance criterion | Test | File | Fails without the change |
|----------------------|------|------|--------------------------|

## Phases
### Phase 1 - <name>
- **Changes**: <files>
- **Exit criterion**: <how to know it worked>
- **Rollback**: <how to undo it alone>

### Phase 2 - <name>
...

## Validation commands
```bash
<only commands that exist>
```

## Definition of done
- [ ] <condition>

## Open questions
- <question, and what it blocks>
```

## Completion criteria

- A reviewer can approve or reject the plan without reading the code.
- Every phase can be reverted independently.
- Every acceptance criterion has a test.
- Every command listed exists in the project.
- No production code was written.
